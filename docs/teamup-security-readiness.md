# TeamUp Step 9E security policy and verification

## Audited architecture

Routes are mounted at `/api/teamup` in `backend/src/routes/index.ts`. Controllers validate IDs and bodies and derive the application user ID from `request.auth.user.id`. `createAuthenticationMiddleware` verifies Supabase identity and resolves the current database user; non-ACTIVE users are rejected. Optional-auth discovery/detail reads allow anonymous callers, but reject an invalid supplied credential or inactive authenticated account. Neither ADMIN nor MODERATOR has an owner bypass in TeamUp.

`TeamUp` uses PostgreSQL JSONB arrays for applications and members, not separate application/member tables. Owner-inclusive capacity is `members.length + 1`. Supported statuses are OPEN, FULL, COMPLETED and ARCHIVED. There are no withdrawal, removal, invitation, transfer-of-ownership, delete, or standalone private-member endpoints. Reapplication is prohibited for every existing application status, including REJECTED.

New TEAMUP messaging contexts require a visible ACTIVE-owned project and two distinct ACTIVE current participants (owner or members). There is no lifecycle recruitment restriction on legitimate team collaboration. Former members/unrelated users cannot open new contexts. Existing participant-authorized conversations/history are preserved; this change does not retrospectively revoke conversations or alter encryption.

## Confirmed gaps and corrections

- Ownership and caller authentication were ALREADY PROTECTED. HTTP regression tests now exercise the actual router, middleware and controller with isolated dependencies, including role-name non-bypass and rejected client ownership fields.
- Application lists, review, lifecycle and workspace omitted moderation/owner eligibility predicates. These are now enforced consistently.
- Creation relied on middleware account freshness; update/lifecycle checks and writes were separated. All privileged writes now check authoritative state within serializable transactions.
- Submissions lacked deadline checks and owner eligibility. A regression reproduced an expired submission being written before remediation.
- Acceptance already used Serializable isolation and checked capacity; it lacked consistent moderation/account restrictions and a bounded serialization retry/error contract. Those are now added. Existing JSONB state is retained; membership is added once with the accepted application in the same write.
- Rejection on COMPLETED/ARCHIVED was previously possible. This ambiguous privileged mutation now fails closed with `TEAMUP_PROJECT_NOT_RECRUITING`; historical application reads remain available. Existing frontend error presentation can display this rejection, though owner controls may still be shown on historical projects.
- Project suggestions lacked ACTIVE-owner, expiry, capacity and existing-application filtering. Owner-scoped suggestions lacked owner freshness and applicant exclusions and could suggest recruitment for FULL projects. Both now enforce actual recruitment eligibility before scoring.
- Hidden owner profiles previously could be projected through TeamUp identity summaries. Their avatar/department/name now use the existing neutral identity fallback; candidate profiles remain explicitly visible-only. No private contact/resume fields are selected.

## Deadline and concurrency semantics

`deadline` is PostgreSQL DATE. Validation accepts real YYYY-MM-DD dates and stores UTC midnight. A deadline expires when its UTC date is lexically earlier than the current UTC date. Its entire stated day remains eligible, regardless of server local timezone. Null means no deadline. Existing pending applications may be reviewed after expiry; edits do not erase relationships or impose a future-date requirement.

Creation, updates, submission, review and lifecycle changes use Serializable transactions. PostgreSQL `FOR SHARE` locks on relevant user rows prevent suspension/deactivation committing between the authoritative account check and write. Ownership, lifecycle, capacity, applications and membership are re-read on every transaction attempt. Existing conflicting project writes are handled by PostgreSQL Serializable isolation. Retry P2034 and raw-query serialization/deadlock SQLSTATEs 40001/40P01 up to three total attempts; exhaustion returns 409 `TEAMUP_CONCURRENCY_CONFLICT`. Notifications stay outside the retried transaction and are attempted only after successful mutation.

New actionable errors are 409 `TEAMUP_APPLICATION_DEADLINE_EXPIRED`, `TEAMUP_PROJECT_NOT_RECRUITING`, and `TEAMUP_CONCURRENCY_CONFLICT`. Existing error envelopes, routes, success DTOs, input fields, rankings and result limits are retained. Hidden/missing projects use existing concealed not-found/closed behavior. No role elevation was added.

## Verification and production gate

`teamup-security.test.ts` tests repository decisions, no-write negatives, account changes on retry, rollback/replay, notification placement, and real HTTP routing with isolated database/identity dependencies. `teamup-recommendation-security.test.ts` exercises actual recommendation service filtering/projections with scoring stubbed to avoid network inference. Existing authentication, service, scoring and frontend suites remain regression coverage.

`teamup-security-postgres.test.ts` is an opt-in, disposable database integration suite. It never reads DATABASE_URL as its test connection and accepts only loopback `TEAMUP_TEST_DATABASE_URL` with database name `campusconnect_teamup_test_*`. It refuses a database containing public tables, then creates minimal fixture tables. It includes simultaneous acceptances/submissions and real JSONB/Serializable behavior. It is not a migration and must never target a project database.
