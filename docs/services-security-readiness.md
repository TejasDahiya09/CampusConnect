# Campus Services Step 10A.1 security foundation

## Scope and verified policies

Services keeps its existing endpoints, pricing model, request statuses and success envelopes. The optional `viewerCanRequest` response field is additive and separates current eligibility from `viewerRequestStatus`, which now represents the latest historical request. No Prisma schema or migrations changed. Frontend changes are limited to re-request controls, pending submission state and handling messaging rejection; no stylesheet or approved other-module presentation changed.

All authenticated routes retain Supabase identity verification and current ACTIVE application-account middleware. Controllers derive identity from the authenticated request, reject client ownership fields and validate UUIDs. ADMIN/MODERATOR have no provider-ownership bypass. Services transaction account checks are domain invariants, not a separate authentication mechanism.

## Transaction and lifecycle protection

`services-policy.ts` provides bounded Serializable transactions (three total attempts, 2-second acquisition limit, 5-second transaction timeout) and current account checks. `FOR SHARE` account locks prevent suspension/deactivation committing between authorization and a write. Ownership, service lifecycle/visibility and request state are re-read on every retry. Conflicting project/service writes cannot silently overwrite an ARCHIVED state or an already-finalized request. No network operation or notification delivery occurs while the mutation transaction holds locks.

Retry only Prisma P2034 or raw P2010 carrying PostgreSQL SQLSTATE 40001/40P01, including adapter-pg's `driverAdapterError.cause.originalCode` representation. Authorization, validation and business-rule failures are not retried. Exhaustion returns HTTP 409 `SERVICE_CONCURRENCY_CONFLICT`; established duplicate/lifecycle error codes remain. No request or notification is created when a provider/requester eligibility check fails. New-request notification recipients/titles come from the committed transaction result, not a stale preliminary public lookup; this internal metadata is stripped before returning the original request DTO.

Requests remain JSONB-backed. Serializable check-and-append enforces one active PENDING/ACCEPTED request per requester/service through these repository methods. Reviews and completion rewrite the request collection atomically. New requests after rejection/completion receive new IDs. Latest request presentation uses creation instants; equal timestamps use later append position. Active-request eligibility is checked independently of latest historical status.

## Privacy and historical access

`servicePerson` preserves the existing ID/avatar/department/displayName shape. Only an ACTIVE account with a VISIBLE profile supplies avatar, department or name. Hidden/inactive identities retain their necessary workflow ID with null attributes and `CampusConnect student` fallback. This applies to service provider projections, requester workspace identities, SERVICE conversation participants and SERVICE message-notification sender names. Global Search's Services provider-name projection also redacts hidden profiles. No email, phone, enrollment ID, resume or new private field was added.

Historical participant access does not make hidden records publicly discoverable. Anonymous/unrelated detail reads still conceal them. Existing profile restrictions do not erase requests, original authorized notes, services or conversation records. There is no new student verification badge, payment or media capability.

## SERVICE messaging

The context ID remains the request ID, never the service listing ID. New conversations require an ACCEPTED/COMPLETED request, the exact provider/requester pair, both accounts ACTIVE and a VISIBLE service. PAUSED/ARCHIVED services may still support accepted-request collaboration. Hidden services cannot open new contexts; existing participant-authorized conversation history is preserved.

Conversation creation now rechecks this policy inside its own Serializable transaction, with account and service share locks, before the existing canonical-pair conversation upsert. The existing database conversation unique constraint prevents duplicate contexts. Encryption and historical conversation authorization are unchanged.

## Pricing and frontend compatibility

Price bounds and FREE/FIXED predicates now intersect instead of overriding one another. FREE means zero, FIXED means positive, NEGOTIABLE means null. Numeric bounds with NEGOTIABLE, inverted ranges, FREE ranges excluding zero, and FIXED ranges whose maximum is zero return validation errors. Bounds are non-negative, at most 10,000,000, with at most two decimals and bounded string length. Query names, sorts and pagination remain unchanged; no category taxonomy was added.

The detail page displays latest historical status while allowing a new request after REJECTED/COMPLETED when the server permits it. PENDING/ACCEPTED, provider-self, inactive availability and explicit server denial prevent submission controls. Submission pending state disables its button; failed submissions restore it. SERVICE messaging failures use existing workspace error feedback instead of an unhandled promise rejection. Rendered component tests cover these controls without pretending to be browser visual QA.

## Actual PostgreSQL verification

`services-security-postgres.test.ts` requires `SERVICES_TEST_DATABASE_URL`; it never falls back to DATABASE_URL. It accepts only postgres on 127.0.0.1:5433 with a `campusconnect_services_test_*` name, rejects URL overrides, and requires DATABASE_URL to equal the same isolated target before running. Read-only server identity and empty-public-schema checks precede fixture DDL. Child processes explicitly disable dotenv loading of normal application/TeamUp configuration. The private credential file is parsed without logging its contents; only credentials/verified host are reused, with database `/postgres` for provisioning and a new Services name for each run. No existing TeamUp database is opened or modified.

The suite uses synthetic users, services, requests, conversation rows and notification intents on PostgreSQL 17.11. It closes both Prisma clients and pg pools. Test-only functions/triggers/sequences are removed in finally blocks. Disposable databases and fixture records are retained for inspection; no existing database is dropped/reset. Fixture DDL is not a production Prisma migration.

Thirty-one actual database cases cover inactive provider/requester guards, cross-provider and request-ID attacks, historical access/completion, re-request history, synchronized duplicate submissions, competing decisions, lifecycle/ownership/moderation races, account-lock contention, real serialization retry/exhaustion, rollback, notification intent count, hidden profile projections, numeric price filtering, exact messaging participants, concurrent unique conversation creation and real HTTP routing with isolated verified-identity dependencies. Barriers force competing transactions to read the same snapshot; lock races observe `pg_blocking_pids`; test-only SQLSTATE 40001 triggers and persistent sequence counters demonstrate retries. Assertions inspect persisted rows, not only responses. No real notification delivery or paid AI inference is used.

The full backend run includes the Services database suite. TeamUp's 21 opt-in database cases and the separately gated live Lost & Found FastAPI case are skipped to avoid touching existing TeamUp databases or invoking unrelated live services. Ordinary TeamUp/auth/search/profile/messaging regression tests still run. Offline S3 signing checks use synthetic environment-only credentials; no AWS operations are performed.

## Residual limitations and release verdict

These corrections and local PostgreSQL tests satisfy the scoped Services security/concurrency gate. They are not a production load test, full Supabase-schema rehearsal or external notification-delivery verification. JSONB requests still lack independent relational uniqueness/foreign-key constraints: writers bypassing protected repository transactions can violate invariants. Workspace queries remain unpaginated, and notification delivery is best-effort rather than outbox-backed. No schema change is required for this patch. Normal deployment/environment review remains separate; no deployment or UI modernization is authorized by this work.
